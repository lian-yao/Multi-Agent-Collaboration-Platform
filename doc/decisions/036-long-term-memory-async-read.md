# ADR-036: 长期记忆的异步读取（预取 + 进程内缓存，永不阻塞主流程）

- 状态：已接受（设计）；读取管道随本轮落地，**写入触发与记忆归属仍待定**（见 §待定）
- 日期：2026-09-23
- 相关：ADR-005（记忆数据结构）、ADR-019（会话记忆接线）、ADR-035（本地服务形态）

## 背景

`app/memory/` 的**长期记忆**（Redis Hash `agent:{id}:memory`，无 TTL）自 `69960e1` 就实现
完毕并有单测，但一直没有调用方（ADR-005 §「未改变的边界」、`doc/data-model.md` §5）；
使用者实测反馈「同一个会话不记得我之前说过什么」时，也只有会话记忆那条链被接上。

现在的要求是：**通过异步的方式读取用户信息与偏好，不要影响主进程**。

这条要求点在了要害上。长期记忆与会话记忆的性质不同：

- **会话记忆是必需上下文**：同一会话的上一轮说了什么，缺了就是「失忆」（第七轮刚修的那个
  bug），所以它在阶段活动里同步读，读不到也要明确降级；
- **长期记忆是增强**：偏好与背景信息有则更好、没有也能跑。为它让关键路径多等一次网络
  往返（甚至等一次超时）是拿主流程的稳定性去换锦上添花——这正是本条要避免的。

## 决策

### 1. 预取在前台之外，读取只碰内存

`app/orchestration/long_term.py`：

- `prefetch(ids)`：**在后台线程里**把若干 id 的长期记忆读进进程内缓存（带 TTL，默认 5 分钟）。
  同一 id 只允许一个在途请求，避免线程风暴；
- `preference_block(id)`：**只读缓存**。缓存未就绪、已过期、读失败——一律返回空串。
  **永不阻塞、永不抛异常**；
- 调用点：消息受理后（`POST /sessions/{id}/messages` 受理成功、写会话记忆的同一处）预取一次，
  覆盖全部角色；阶段真正执行时通常已过数秒，缓存是热的。冷启动/预取失败时该轮没有长期记忆，
  提示词与接线前**逐字一致**。

记忆实现的取用口留在本模块（`set_memory_factory`，默认 `build_long_term_memory`）：
与 `app/memory/runtime.py` 的会话记忆同一模式，但**不改记忆层**——本轮只调用既有
`list_entries()`。测试用它注入替身，用例不依赖真实 Redis（`tests/unit|integration` 的
autouse fixture 都已加上，与 ADR-019 对会话记忆的处理一致）。

规划节点的记忆 id 用**保留值 `planner`**（`dynamic_graph.PLANNER_MEMORY_ID`）：规划是平台
自己的节点、不对应任何已登记角色，借用某个角色的 id 会让「收集 Agent 的偏好」悄悄影响规划。

### 2. 注入位置与会话历史并列、在其之前

提示词前缀顺序：`【长期记忆（跨会话）】` → `【会话历史（最近 N 条）】` → 本轮任务/上游结果。

理由：长期记忆是**跨会话的稳定约束**（偏好、背景），会话历史是本轮对话的即时上下文；
模型看到的顺序应当与"约束 → 上下文 → 当前指令"的优先级一致。两段渲染都在
`app/orchestration/context.py`，两条编排（静态三步 / 动态）共用，避免再出现第七轮那种
「一条接了、另一条没接」的分叉。

### 3. 记忆归属：**暂按角色（agent_id）读**，用户维度列为本 ADR 的待定项

现有键是 `agent:{id}:memory`（ADR-005 只定义了「会话记忆」与「长期记忆」两个键），
按**角色**存。而本轮需求说的是「**用户**信息与偏好」——那是使用者维度。

本轮先按现有键读（角色 id → 该角色的长期记忆），因为它不改数据契约、可立即落地；
但要把差异讲清楚：**同一个使用者的偏好会被按角色复制 N 份**，且 `user_id` 目前
**没有进 Workflow 链路**（`sessions.user_id` 只在 API 层创建会话时用），要按用户存就得
先把它透传下去。

## 待定（需要使用者拍板，不在本轮实现）

1. **记忆归属**：新增 `user:{id}:profile`（要改 ADR-005 与 `doc/data-model.md` §5、
   并把 `user_id` 透传进 Workflow），还是复用角色键（现状，偏好按角色各存一份）？
2. **写入触发**：现在**没有任何写入方**，所以读取管道即使就绪，短期也读不到东西。
   候选：显式「记住这个」交互（用户说、平台落库，最小且可解释）／独立抽取流程（要额外的
   模型调用与成本控制）／管理接口手工登记。
3. **审计与删除**：`doc/data-model.md` §5 写着「记忆层写入前先落审计」；长期记忆**无 TTL**，
   所以必须有查看与删除入口，否则使用者无法收回模型记住的东西。

## 备选方案

- **阶段内同步读**：实现最省事，但等于把长期记忆放进关键路径——Redis 抖动就拖慢每一次
  执行，与本条需求直接冲突。
- **把长期记忆塞进 Workflow 载荷**：与 ADR-019 对会话历史的判断一致（否决）——状体会被
  反复序列化放大，且提交到执行之间记忆会过期。
- **引入向量检索**：设计文档把它标为可选；本期先做结构化偏好记录。要做需另开 ADR。

## 影响

- 新增 `app/orchestration/long_term.py`（预取 + 缓存 + 渲染取用）；`context.py` 增加
  `long_term_block(entries)` 渲染，两条编排共用；
- `pipeline_graph._role_input` 与 `dynamic_graph.step_input` 增加 `preferences` 参数，
  由各自的调用方按角色 id 传入；静态与动态链路的行为保持一致；
- `app/api/main.py::send_message` 受理后触发一次预取（后台线程，失败只记日志）；
- 记忆层本身（`app/memory/`，成员 C 的模块）**不改**——本轮只调用既有 `list_entries()`；
- 不阻塞、不新增失败面：预取失败等价于「这一轮没有长期记忆」。
