# ADR-037: 问题改写（前置步骤）+ 角色提示词与软件对齐

- 状态：已接受（设计）；实现随后落地
- 日期：2026-09-23
- 相关：ADR-006（角色提示词）、ADR-019（会话记忆接线 / 动态编排）、
  ADR-036（长期记忆异步读取）、ADR-033（工作区与审批）、ADR-009（工具调用）

## 背景

使用者的要求是两条：**「增加一步问题改写，把用户的输入，通过会话上下文，改写的更完整」**，
以及**「修改一下提示词，每个 agent 的提示词，使其更符合现在的软件」**。

现状的两个问题都很具体：

1. **用户的输入直接当任务用**。静态链路把原文交给收集阶段当「用户任务」，动态链路把原文交给
   规划 Agent 当「用户任务」；历史与长期记忆只是**挂在前面的一坨上下文**（ADR-019/036），
   要模型自己从上下文里推断「这句话指的是什么」。短输入尤其吃亏——「重试」「再详细一点」
   这类话，下游只能给出泛泛的回答。第七轮修记忆问题时那条实测就是同一个病根：
   助手答「本会话没有其他消息」。
2. **角色提示词与软件脱节**。三个角色现在只描述「收集 / 分析 / 报告」这套抽象分工，
   完全没提平台**真实给到它们**的能力与约束：会话工作区文件工具、附件、按需调用的 MCP 工具、
   网页搜索、破坏性动作要人工审批、路径只能在会话工作区内。模型不知道手上有这些，
   自然也不会用。

## 决策

### 1. 新增一步「问题改写」，作为一次执行的**前置步骤**

在一次执行开始前跑一次改写（两条链路共用同一份实现 `app/orchestration/rewrite.py`）：

- **输入**：本轮用户原文 + 会话历史（最近 N 条、剔除本轮，口径同 ADR-019）+
  长期记忆（使用者偏好，ADR-036）+ 本轮**附件文件名**（只给名字，不给正文：
  正文进改写提示词没有收益，却会把 token 花在重复内容上）；
- **输出**：一段**自包含**的任务描述——补全指代、写清目标与约束、点明期望交付物；
- **降级**：模型调用失败、输出为空、或输出与原文无实质差别时，**退回原文**
  （`rewrite_source = "original"`），绝不阻塞执行、绝不抛错。这与 ADR-019/036 一脉相承：
  这一段是**增强**，不是必需。

### 2. 不新增第 4 个 `PipelineStage`

`PipelineStage` 是固定三元组（collect / analyze / report），有四处按它取值：
Dapr 子工作流实例 ID（`{workflow_id}:{stage}`，断点续跑靠它稳定）、阶段状态键
`agentrun:workflow:{workflow_id}:{stage}`、`GET /stage-trace` 的出参、以及前端的阶段列表。
把改写做成"第 4 个阶段"会同时改这四处，而它**不是协作阶段**：没有角色、不产出交付物，
只是把输入说清楚。

因此改写是**前置步骤**：用 `observed_stage(stage="rewrite")` 进指标与追踪，
`log_event("run.rewrite")` 留审计（原文长度、改写后长度、是否退回原文）。
前端要展示改写结果时，从下面第 3 条的 checkpoint 字段读，不需要新的阶段契约。

### 3. 改写结果落盘，可审计

`PipelineState` / `DynamicPipelineState` 增加**可选**字段 `rewritten_task` 与
`rewrite_source`，随 `workflow_runs.checkpoint` 一起可见（前端已按 checkpoint 渲染，
新增字段向后兼容；老状态反序列化时取默认值）。

### 4. 角色提示词与规划提示词按**软件现状**重写

每个角色的 system prompt 必须写清三件事，缺一不可：

1. **它在这个平台里的真实位置**：本次执行的第几步、上游给什么、下游要什么；
2. **手上真有什么**：会话工作区文件工具（`list_work_files` / `read_work_file`；可写档位下
   另有 `write_work_file` / `make_work_dir` / `move_work_entry`）、附件（图片需要模型支持
   视觉输入）、按需发现并调用的 MCP 工具、网页搜索；
3. **边界与纪律**：文件只能碰**会话工作区**内的路径，越界会被服务端直接拒绝；
   覆盖与删除是**人工审批**、不是失败（不要因此重试或改写结论）；不臆造来源与数据；
   不复述上游原文，产出要能被下游/使用者直接使用。

规划 Agent 的 prompt 同样补齐：列出各角色**实际能力**（而不只是名字），
说明 `instruction` 会直接作为该角色的任务说明，并要求最后一步产出面向用户的交付物。

## 备选方案

- **把改写塞进规划节点**（动态链路顺手做）：静态链路没有规划节点，两条链路的输入质量会分叉；
  而且规划关注"谁参与、按什么顺序"，改写关注"这句话到底要什么"——两件事混在一个提示词里，
  两边都写不好。
- **在 API 受理消息时改写**：会把一次模型调用塞进 HTTP 请求的关键路径（受理接口必须快，
  且失败要可降级），并让改写发生在编排之外、脱离 Workflow 的重放语义。否决。
- **让前端在提交前改写**：把"补全指代"变成用户要看的额外一步，且前端拿不到本会话的完整
  历史与长期记忆（那两份在服务端）。否决。
- **新增第 4 个阶段**：见 §2，四处契约同时变，收益只是"在阶段列表里多一行"。

## 影响

- 新增 `app/orchestration/rewrite.py`（提示词 + `rewrite_task()`）；
- `app/orchestration/pipeline.py` / `dynamic_graph.py`：状态增加两个可选字段；
  `pipeline_checkpoint_summary` / `dynamic_checkpoint_summary` 带上改写结果；
- `app/workflows/pipeline.py` / `app/workflows/dynamic.py`：各加一个前置活动并透传；
- `app/agents/roles.py`：三个 system prompt 重写；`dynamic_graph.planner_prompt` 同步；
- 每次执行多一次模型调用（改写），失败即退回原文——**成本换输入质量**，可接受；
- 既有断言不受影响：没有历史/偏好时改写提示词的上下文段为空（与 ADR-019 同口径）。
