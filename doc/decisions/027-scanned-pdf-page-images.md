# ADR-027: 扫描版 PDF 走页面图像，不引 OCR 引擎

状态：已接受

## 背景

ADR-021 定下「附件按**怎么被模型消费**分类」，PDF 走 `document` 分支：服务端尽力抽取正文，
抽不出来就报 `failed`（`doc/api.md` §5.16.1）。这条策略在一个真实的用户场景上留下了一个洞：

**扫描版 PDF 和「两种内嵌字体子集码冲突」的 PDF，模型看到的是零内容。** 前者的字节在库里、
文件名在清单里、气泡上有那个附件——但它对回答毫无贡献。ADR-024 只解决了「用户能拿回原件」，
没有解决「模型能读到内容」。用户提出的问题是：这类文件是不是必须上 OCR？

顺带记录一个反直觉的结论：本项目**连打开渲染器都不需要 OCR**。视觉通路早就付过成本
（ADR-021 的 `image_url` 内容块），`doc/evals/vision.md` 的 10 例答案唯一的图片用例实测
**10/10**。把页面渲成图交给它读，比在服务端做文字识别更省事、更准，也更诚实。

## 决策

**抽不出正文的 PDF，把页面渲染成 PNG，作为普通图片附件走既有的视觉通路。不引 OCR 引擎。**

### 1. 为什么是「渲染 + 视觉模型」而不是 OCR

- **OCR 的错误形态更糟**。识别错一个字产出的是一句**通顺但错误**的话，模型会当真；
  而页面图像里模型自己会做视觉判断，看不清时它倾向于说"这块字太小/太糊"。
  本项目的文本抽取已经踩过一次同样的坑（字体码冲突时会产出通顺但全错的句子，
  见 `app/attachments/extract.py::_pdf_to_unicode_map`），刻意没有再犯一次。
- **版面本身是信息**。表格线、栏位、印章、勾选框在 OCR 的纯文本输出里全丢了，
  而在页面图像里原样保留。
- **依赖与许可**：成熟的中文 OCR 引擎要么体积与模型文件巨大（PaddleOCR / 各种模型权重），
  要么要额外进程与字体（Tesseract）。视觉通路则是**已经在用**的能力，边际成本只有渲染。
- **诚实**：我们不需要宣称"我们读懂了这份扫描件"，只需要说"我们把它的页面交给了模型"。

### 2. 渲染器选 pypdfium2

| 候选 | 判断 |
| --- | --- |
| **pypdfium2** | **采用**。BSD-3 / Apache-2.0 双许可；wheel 自带 pdfium 二进制（约 3.7 MiB），无系统依赖；直接从字节渲染，不需要落临时文件 |
| PyMuPDF | 否决：**AGPL**。嵌进一个要交付的工程会传染许可 |
| pdf2image | 否决：它自己不做渲染，调 `poppler` 的外部可执行文件——容器里要多装一个系统包 |
| 浏览器 / 无头 Chromium | 否决：与现有镜像和启动方式完全不搭（ADR-023 的 compose 里没有浏览器） |

### 3. 上游只**探测**，执行阶段才整份渲染

- `extract_pdf` 抽不到正文时，只渲**第 1 页**（实测 0.02–0.3 秒）来判断"这份文件在这台机器上
  能不能渲出来"，据此决定 `status`；
- 真正的整份渲染发生在**执行阶段**（`prepare.py::_expand_scanned_pdf`），页面图在那里被展开成
  逐页载荷。

为什么不在上传时就整份渲好存库：页面图唯一的用途是送进模型请求，上传时渲出来得**新加一张表**
为它占库容与生命周期管理，而原件本来就在 `data` 里（ADR-024），派生结果随时能重来。
代价是每次执行重渲一遍——有界（只对抽不出正文的 PDF 发生，页数与体积都有上限），
换来的是零 schema 变更。

### 4. PNG 自己编码，不引 Pillow，也不依赖 numpy

pdfium 交出来的是**裸像素缓冲**（实测 `n_channels=3`、`stride=width*3`，纯 RGB 无 alpha），
而 PNG 的容器就是 `IHDR + IDAT(zlib) + IEND`，标准库能拼（`app/attachments/render.py::encode_png`）。
引 Pillow 只为一次 `save()`，要多扛一个几十 MB 的依赖（与 `extract.py` 不引 `python-docx` 同一条理由）。

**特别记一笔：不能依赖 numpy。** 它在 `.venv` 里存在只是因为别的包把它带了进来，
`pyproject.toml` 里没有它——用 `to_numpy()` 会写出一个"本地能跑、镜像里炸"的渲染器。
因此 `stride` 的填充也自己处理（按行切片再插 filter 字节）。

### 5. 上限（都是**硬**上限，超了就丢页并如实报告）

| 值 | 取这个值的理由 |
| --- | --- |
| 每次最多 **5 页** | 每页 base64 后约 0.3–0.5 MB，5 页已经与"单张图片 5 MB 量级"的模型侧上限同一量级；再多该让用户拆开传 |
| 渲染倍率 **1.7**（≈122 dpi） | 视觉模型会把图缩到长边 1.5k 像素上下再切块：渲得更大只是被丢掉，渲得更小则 8pt 小字会糊 |
| 长边 **2000 px** 硬顶 | 兜住 A0 图纸这类超大页面，避免为渲一页先分配上百 MB 位图 |
| 单页 **1.2 MB** | 超了按 0.9 倍重渲一次；仍超则丢这一页并计数 |
| 合计 **4 MB** | 到顶就停，剩下的页计入未带上 |

**丢页必须说出去**：载荷名字写成 `xxx.pdf · 第1页/共9页`，模型据此知道自己看的是前 5 页；
`error` 里也写「全 9 页，只带前 5 页」。宁可告诉它"没看全"，也不能让它以为这就是全部。

### 6. 状态语义：「有没有正文」与「成不成功」从此分开

这类 PDF 的 `status` 是 **`ready`**、`text_content` 是 **`None`**、`error` 里放一句**降级说明**。
`ready` + `error` 不是新用法——`extract_plain_text` 早就这么用（用替换字符解码时给一句说明）。

- 前端 `describeAttachment` 必须显示这句说明：`ready` 却什么都不说，用户会以为正文是被正常
  提取出来的（这正是本项目一直在防的"假信号"）。本轮同步改了前端与冒烟。
- 清单里 `failed` 与 `ready+说明` 是两种不同的表述，别再合成一句。

### 7. 「字体码冲突」也走这条路

`two-font-heading.pdf` 这条夹具恰好证明渲染**不是 OCR 的降级品**：它渲染出来完全可读
（`Two Font Heading` / `The body uses a second embedded font subset.`），而文本通路出于**正确性**
刻意不给。所以规则简化成一条：**PDF 抽不出正文 → 渲成页面图**，不再区分是哪一种原因；
区别只留在那句降级说明里（"没有文本层" vs "字符码冲突，无法安全还原文字"）。

## 备选方案

- **上 OCR 引擎（Tesseract / PaddleOCR / 云 OCR）**。否决：见「决策 1」。另外云 OCR 会把附件
  内容送到第三方，与"内容不出平台"的既有取向冲突。
- **上传时整份渲染并把页面图存进新表**。否决：见「决策 3」。它会顺带引入页面图的生命周期
  （级联、体积、清理）与一次 schema 变更，而收益只是省掉每次执行的几十毫秒。
- **把多页拼成一张长图**。否决：视觉模型会把长边缩到 1.5k 像素上下，5 页拼起来等于每页只剩
  约 300px 高——文字全糊。**页数少不等于看全，看得清才算。**
- **用 `to_pil()` 渲染（即引 Pillow）**。否决：见「决策 4」。
- **给码冲突的 PDF 分字体建表**（跟踪内容流里的 `/Fx Tf` 并回解页面 `/Resources`）。
  仍然不做：那是另一次改动，而且现在渲染已经能把这类文件读出来，优先级更低。
- **检测"渲染结果是空白页"就不发**。本轮没做：可靠的空白判断要按像素统计（没有 numpy 时
  在 Python 里逐像素是慢路径），而误判代价是**丢掉真实内容**——一份 20 KB 的空白页图，
  让模型自己说"这一页是空白的"更划算。
- **让 `read_session_file` 工具也能读扫描件**。做不到：工具结果只能是文本，无法回传图片。
  该工具会看到 `status=ready` + `text=null` + 那句降级说明，用户/模型据此知道要走视觉通路。

## 代价（如实记录）

- **超过 5 页的部分看不到**：这是硬上限，只如实报告，不悄悄截断。
- **每页都进 token 账**：一份 5 页扫描件 ≈ 5 张图的视觉 token。ADR-021 已经为此把"附件只注入
  接收原始任务的根步骤"定成规则，扫描件沿用同一条。
- **每次执行重渲**：不做进程内缓存，避免为图片字节引入第二份生命周期。
- **容器必须带上 pdfium**：`uv sync --frozen` 会从 `uv.lock` 装（已加 `pypdfium2==5.13.0`），
  但**镜像必须重建**才生效；渲染组件缺失时降级为 `failed` 并明说"服务器缺少 PDF 渲染组件"。
- **上传时的探测与执行时的渲染可能不一致**：探测成功、执行时失败的极端情况（组件被换掉、
  文档被改成加密）会让这一次执行拿不到内容。此时载荷**降级成 `failed` 并写明「页面转图失败」**，
  而不是沿用上传时那句"已改用页面图像提供"——界面上一切正常、模型却两手空空，正是要防的假信号。
